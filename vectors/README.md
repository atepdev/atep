# ATEP test vectors

443 vectors in 28 categories, the executable form of the ATEP specification ([Draft 08](../spec/ATEP-Specification-Draft-08.md), section 12; the 436 vectors of Draft 07 are unchanged, the one added in Draft 08 follows them and the six after it close known gaps of section 12: RT32 (two vectors, `srl-context`), RT34 (two vectors), RT35 and SU27, the last six of the manifest, in the categories `srl-context`, `retired-negative`, `retired-positive` and `successor-positive`; they are not yet in a published draft, and Draft 09 will say so) for the `ATEP-1` suite. Where this README and a vector disagree, the vector wins. Every vector is a set of three files and the list of all of them, with the SHA-256 of each CBOR file, is `manifest.json`. The formats of the categories added after the first 200 vectors are in section 12 of the spec and in the addenda at the end of this file; the reasoning behind the anchoring and discovery vectors is in [`ANCHOR-DISCOVERY-NOTES.md`](ANCHOR-DISCOVERY-NOTES.md) and behind `retired` and `successor` in [`RETIRED-SUCCESSOR-NOTES.md`](RETIRED-SUCCESSOR-NOTES.md). The "Draft N" labels below name the internal working draft in which a behavior was introduced (Appendix A of the spec explains the numbering).

All keys in the vectors are deterministic public test keys derived from the fixed seeds listed in every `inputs` (see "Fixed seeds"). Never use them for anything real.

The vectors are the executable form of the spec. An independent implementation is conformant for M1 when it reproduces every byte of the `identity`, `signing`, `verify-*` and `encryption` vectors and returns every expected result, for M2 when it also passes the `attestation`, `chain-*`, `srl`, `log` (checkpoints and inclusion proofs) and `atep-r-*` vectors, and for M3 (a log or monitor implementation) when it also passes the consistency proof, checkpoint schema and split view vectors of the `log` category. They were generated by the Rust reference implementation and cross-checked for Ed25519, X25519, HKDF-SHA-256, AES-256-GCM, the Agent ID derivation, the Sig_structure, the attestation and SRL schemas and the RFC 9162 inclusion proof with the independent Python script `crosscheck.py` in this directory (needs `pip install cryptography`). See "M2 cross-check coverage" below for what is not independently checked. The ML-DSA-65 and ML-KEM-768 values rest on the RustCrypto `ml-dsa` 0.1.1 and `ml-kem` 0.3.2 crates.

Regenerate with `cargo run -p atep-core --bin atep-vectors -- generate vectors` and check any directory with `... -- check vectors` (run from `rust/`, paths relative to your cwd). Generation is a pure function of fixed seeds: running it twice gives identical bytes.

## Layout

```
vectors/
  manifest.json                      list of every vector with the SHA-256 of its CBOR file
  identity/<name>.{cbor,json,expected.json}
  signing/<name>.{...}
  verify-positive/<name>.{...}
  verify-negative/<name>.{...}
  encryption/<name>.{...}
  attestation/<name>.{...}           M2: attestation issuance
  chain-positive/<name>.{...}        M2: step 9 accepted
  chain-negative/<name>.{...}        M2: step 9 (or 8) rejected
  srl/<name>.{...}                   M2: signed revocation lists
  log/<name>.{...}                   M2: checkpoints and inclusion proofs; M3: consistency proofs, split views
  atep-r-positive/<name>.{...}       M2: ATEP-R accepted
  atep-r-negative/<name>.{...}       M2: ATEP-R rejected
  retired-positive/<name>.{...}      Draft 04: `retired` accepted
  retired-negative/<name>.{...}      Draft 04: `retired` rejected
  successor-positive/<name>.{...}    Draft 04: `successor` accepted
  successor-negative/<name>.{...}    Draft 04: `successor` rejected
  srl-context/<name>.{...}           Draft 04: SRL loading in the verifier's context
  log-admission/<name>.{...}         Draft 04: log admission (retired, successor)
  monitor/<name>.{...}               Draft 04: monitor alert `successor_chain`
  checkpoint-hash/<name>.{...}       Draft 05: canonical checkpoint hash
  anchor-record/<name>.{...}         Draft 05: anchor record validation
  chain-id/<name>.{...}              Draft 05: chain identifiers (registered and extension)
  anchor-envelope/<name>.{...}       Draft 05: log-signed anchor envelope check
  anchor-media-type/<name>.{...}     Draft 05: anchor media type at step 1
  require-anchor/<name>.{...}        Draft 05: `require_anchor` policy parsing
  anchor-not-supported/<name>.{...}  Draft 05: `require_anchor` fails closed at step 9
  registry-endpoint/<name>.{...}     Draft 05: `registry-endpoint` claim
  domain-binding/<name>.{...}        Draft 05: domain records (well-known document and DNS TXT)
```

Every vector is three files with the same base name:

* `<name>.cbor`: the object under test, exact bytes. For `identity` it is the canonical bundle, for `signing` a tag 98 envelope, for `verify-*` the envelope handed to the verifier (tag 98 or tag 96), for `encryption` the tag 96 envelope.
* `<name>.json`: JSON debug view of the CBOR (informational, never compared byte for byte by implementations; see "JSON view").
* `<name>.expected.json`: `{name, category, description, cbor_file, cbor_sha256, inputs, expected}`. `inputs` holds everything needed to reproduce or evaluate the vector, `expected` the required output.

All hex is lowercase. All timestamps are Unix seconds. The reference time for all verification vectors is `now = 1800000000`.

## Fixed seeds

Test identities are `alice` (signing keys only), `bob` and `carol` (signing and encryption keys), `mallory` (signing only, used as an attacker), and for M2 the signing-only identities `root` (root issuer), `ca1`, `ca2` (intermediate issuers), `certifier` (second root, safety certifier), `controller` (fleet controller) and `log` (transparency log). In M2 vectors alice is the subject, bob the recipient. Each secret value is `SHA-256("ATEP-vectors-v1/<name>/<field>")` with fields `ed25519`, `mldsa65`, `x25519`, `mlkem768/d`, `mlkem768/z`; the 64 byte ML-KEM seed is `d || z`. The seeds are also written in plain hex in every `inputs`, so an implementation never needs to reproduce this derivation. Nonces are `SHA-256("ATEP-vectors-v1/nonce/<label>")[0..16]`. Payloads are `{"vector": <label>, "note": "ATEP test payload"}` encoded as deterministic CBOR.

Seed meaning: `ed25519` is the RFC 8032 secret key; `mldsa65` is the 32 byte FIPS 204 seed xi used with `ML-DSA.KeyGen_internal`; `x25519` is the 32 byte RFC 7748 scalar (clamped on use); `mlkem768` is the 64 byte FIPS 203 seed `d || z` used with `ML-KEM.KeyGen_internal`.

## CBOR rules

Deterministic encoding per RFC 8949 section 4.2.1: shortest-form integer and length heads, definite lengths only, map keys sorted by bytewise lexicographic order of their encodings, no duplicate keys, no floats, no tags other than 98 and 96. Booleans, null, integers up to 64 bits signed range, byte strings, text strings, arrays and maps are the only types used. Verifiers reject anything else at step 1 (`malformed_cbor`).

## Public key bundle and Agent ID

COSE_Key encodings (all maps, keys integers):

| Key | Encoding |
| --- | --- |
| Ed25519 | `{1: 1, 3: -8, -1: 6, -2: x(32 bytes)}` (kty OKP, alg EdDSA, crv Ed25519) |
| ML-DSA-65 | `{1: 7, 3: -49, -1: pub(1952 bytes)}` (kty AKP, alg ML-DSA-65, provisional) |
| X25519 | `{1: 1, 3: -25, -1: 4, -2: x(32 bytes)}` (alg ECDH-ES+HKDF-256, crv X25519) |
| ML-KEM-768 | `{1: 7, 3: -70010, -1: pub(1184 bytes)}` (provisional private-use alg) |

Bundle: `[ed25519_key, mldsa65_key]` or `[ed25519_key, mldsa65_key, [x25519_key, mlkem768_key]]`. The third element is omitted entirely when there are no encryption keys. The `identity/*.cbor` files are exactly this encoding.

Agent ID = `SHA-256(bundle bytes)`. Text form `atep:` + lowercase RFC 4648 base32 without padding of the 32 bytes (52 characters after the prefix). Alias `did:atep:` + the same string. Parsers accept only the canonical lowercase form.

`identity/*.expected.json`: `agent_id`, `did`, `agent_id_hex`, `bundle_len`, `ed25519_public_hex`, `mldsa65_public_sha256`.

## Envelope (tag 98)

```
98([ body_protected: bstr, unprotected: map, payload: bstr / null, signatures: [sig_ed, sig_pq] ])
sig_x = [ sign_protected: bstr, {}, signature: bstr ]
```

`body_protected` is the bstr wrapping the deterministic encoding of this map:

| Label | Name | Value |
| --- | --- | --- |
| 3 | content type | text |
| -70001 | atep-version | 1 |
| -70002 | signer | 32 byte Agent ID |
| -70003 | issued-at | integer |
| -70004 | expires-at | integer, present only when set |
| -70005 | nonce | 16 bytes |
| -70006 | payload-digest | SHA-256 of the payload, 32 bytes |
| -70007 | suite | `"ATEP-1"` |
| -70014 | command-class | text, only in ATEP-R envelopes (M2) |

`unprotected` is `{}` or a map with `-70008: bundle` (the bundle array above embedded as a CBOR value, not a bstr), and in M2 vectors also `-70009: [envelope, ...]` (inline attestations, tag 98 values embedded as CBOR values) and `-70012: inclusion proof` (see "Log vectors"). The unprotected header is not signed. `payload` is the payload bytes or `null` when detached.

`sign_protected` is the bstr wrapping `{1: alg, 4: kid}` with alg `-8` (EdDSA) or `-49` (ML-DSA-65, provisional) and kid the 32 byte Agent ID. The EdDSA entry comes first.

Both signatures cover the same message, the RFC 9052 section 4.4 Sig_structure for each signature, encoded as the CBOR array

```
["Signature", body_protected, sign_protected, h'', payload]
```

where `body_protected` and `sign_protected` are the bstr contents (the serialized headers) as byte strings, `h''` is the empty external_aad, and `payload` is the actual payload bytes even when detached. Each signature is computed over its own Sig_structure (it differs in `sign_protected`).

* EdDSA: pure Ed25519 (RFC 8032). Verified strictly (`verify_strict` semantics).
* ML-DSA-65: pure ML-DSA, FIPS 204 Algorithm 2 with empty context string and the deterministic variant (rnd = 32 zero bytes). Verification is FIPS 204 Algorithm 3 with empty context.

### Content types and encryption rule

Trust documents may be sent unencrypted: `application/atep-attestation+cbor` (expires-at REQUIRED), `application/atep-srl+cbor`, `application/atep-checkpoint+cbor` (the last two are provisional names). Any other content type, for example `application/atep+cbor`, MUST arrive wrapped in tag 96, otherwise the verifier rejects at step 1.

### `signing/*.expected.json`

`inputs`: `signer_seeds`, `payload_hex`, `content_type`, `nonce_hex`, `issued_at`, `expires_at` (or null), `detached`, `include_bundle`, `mode` (always `deterministic`). `expected`: `signer`, `payload_digest_hex`, `envelope_len`, `envelope_sha256`. Reproduce by building the headers above and signing in the deterministic mode; the result MUST equal the `.cbor` file byte for byte. Note: `data-*` signing vectors are valid signing outputs but are not valid for unencrypted verification.

## Encryption (tag 96)

```
96([ protected: bstr, { 5: iv(12) }, ciphertext: bstr,
     [ [ recipient_protected: bstr, { 4: kid, -1: eph_key, -70013: kem_ct }, h'' ] ] ])
protected           = bstr of {1: 3, -70001: 1, -70007: "ATEP-1"}      ; A256GCM
recipient_protected = bstr of {1: -70011}                              ; ATEP-1 hybrid KEM (provisional)
kid                 = recipient Agent ID (32 bytes)
eph_key             = COSE_Key {1: 1, 3: -25, -1: 4, -2: ephemeral X25519 public key}
kem_ct              = ML-KEM-768 ciphertext (1088 bytes)
```

Procedure (sender):

1. `eph_pub = X25519(eph_sk, basepoint)`; `ss_x = X25519(eph_sk, recipient_x25519_pub)` (reject all zero).
2. `(kem_ct, ss_pq) = ML-KEM-768.Encaps_internal(recipient_mlkem_pub, m)` with the 32 byte randomness `m` (FIPS 203 Algorithm 17).
3. `key = HKDF-SHA-256(salt = empty, ikm = ss_x || ss_pq, info = "ATEP-1-KEM" || eph_pub || recipient_x25519_pub || kem_ct, L = 32)`.
4. `ciphertext = AES-256-GCM(key, iv, plaintext = inner tag 98 envelope bytes, aad = Enc_structure)` where `Enc_structure` is the encoded CBOR array `["Encrypt", protected, h'']` (`protected` as byte string). The ciphertext field holds ciphertext followed by the 16 byte tag.

The recipient reverses this with its X25519 secret and ML-KEM decapsulation key (from the seed). `encryption/*.expected.json`:

* `inputs`: `recipient_seeds`, `inner_envelope_hex` (the signed envelope that was encrypted), `randomness` `{x25519_ephemeral_hex, mlkem_m_hex, iv_hex}`.
* `expected`: `recipient`, `ciphertext_len`, `ciphertext_sha256`, `intermediate` `{eph_x25519_public_hex, mlkem_ciphertext_sha256, ss_x25519_hex, ss_mlkem768_hex, hkdf_info_hex, aes_key_hex}` for locating divergences.

An implementation passes when `encrypt(inner, recipient_public, randomness)` equals the `.cbor` file and `decrypt(cbor, recipient_seeds)` equals `inner_envelope_hex`.

## Verification vectors

`inputs.policy`:

| Field | Meaning |
| --- | --- |
| `now` | verification time |
| `max_skew_secs` | allowed future skew for issued-at (300) |
| `recipient_seeds` | present when the verifier holds a recipient identity (to open tag 96) |
| `known_bundles` | hex of cached signer bundles |
| `seen_nonces` | hex of nonces already seen (step 6) |
| `revocations` | `[{id, reason: retired or compromised, revoked_at}]`, directly supplied identity revocations (step 8) |
| `detached_payload_hex` | out of band payload for detached envelopes |
| `trust` | M2: trust policy object (same format as the policy file of the CLI, see `rust/README.md`); absent means step 9 is skipped |
| `attestations` | M2: hex of attestation envelopes the verifier already holds, in addition to the inline ones |
| `srls` | M2: hex of SRL envelopes in the verifier's cache (each is verified and loaded as in "SRL vectors"); step 8 and step 9 consult them |

`expected` is either

```
{"ok": true, "signer": "atep:...", "content_type": ..., "issued_at": ..., "expires_at": int or null,
 "nonce_hex": ..., "encrypted": bool, "claims": [], "checkpoint": null, "payload_hex": ...}
```

or `{"ok": false, "step": N, "error": "<code>"}`. `step` is the section 10 step that rejected. The `error` codes are stable names; an implementation SHOULD use them but the `step` is the normative part. For M1 vectors `claims` is `[]` and `checkpoint` is `null`. M2 vectors fill them and add the optional keys described below.

Algorithm (section 10, rejecting on the first failure):

1. Decode. Strict deterministic CBOR. Tag 98, or tag 96 wrapping 98. For tag 96 check outer `atep-version` = 1, `suite` = `ATEP-1`, alg = 3 and one hybrid KEM recipient. For tag 98: all required protected fields present with the right types, version 1, suite `ATEP-1`, exactly two signatures, one EdDSA and one ML-DSA-65, attestation content type has expires-at, and an unencrypted envelope has a trust document content type. Order of checks: structure, version, suite, remaining fields, signature shape, expires-at rule, encryption rule.
2. Decrypt (tag 96 only). Needs the recipient identity; recipient kid must equal its Agent ID; any KEM or AEAD failure rejects. The plaintext is decoded as step 1 again (inner must be tag 98).
3. Resolve signer. Bundle from the inline `-70008` entry, else from `known_bundles` by Agent ID. `SHA-256(bundle encoding)` must equal `signer`. Both signature `kid`s must equal `signer`.
4. Both signatures verify over their Sig_structure, EdDSA checked first. A detached payload must be supplied.
5. `issued-at <= now + max_skew_secs` and, if present, `expires-at > now`.
6. `nonce` not in `seen_nonces`.
7. `SHA-256(payload) == payload-digest`.
8. Signer not in `revocations` with `revoked_at <= issued_at`.
9. Policy evaluation. Not part of the M1 vectors; see "Trust policy evaluation" below.
10. Return the result structure.

## Attestation vectors (M2)

`attestation/*.cbor` is an attestation envelope: tag 98, content type `application/atep-attestation+cbor`, `expires-at` present, signed with deterministic ML-DSA. The payload is the deterministic encoding of a map with text keys:

| Key | Type |
| --- | --- |
| `subject` | 32 byte Agent ID |
| `issuer` | 32 byte Agent ID, equal to the envelope `signer` |
| `claim` | claim type URI (text) |
| `data` | map with text keys, claim specific |
| `evidence` | optional, 32 bytes |
| `evidence-uri` | optional, URI |
| `id` | 16 bytes |

Unknown keys, missing keys and wrong types are schema errors. Claim rules on top of the schema: `audited` and `robotics/safety-certified` require `evidence`; `issuer-authority` requires `data.claims`, an array of claim URIs (provisional layout, see the Rust implementation findings).

`inputs`: `issuer_seeds`, `subject`, `claim`, `data_hex` (the encoded `data` map), `evidence_hex` or null, `evidence_uri` or null, `id_hex`, `nonce_hex`, `issued_at`, `expires_at`. `expected`: `issuer`, `payload_hex`, `envelope_len`, `envelope_sha256`. Reproduce by encoding the payload and signing it with `issued_at`, `expires_at`, `nonce_hex` in deterministic mode with the bundle inline; the result MUST equal the `.cbor` file. Lifetime rules checked at issuance: more than 400 days is never allowed, more than 180 days is allowed only for audit-backed claims (`audited`, `safety-certified`, or any attestation with `evidence`).

## Trust policy evaluation (`chain-*`, `atep-r-*`)

These vectors are verification vectors in the format above; the `cbor` is always an encrypted data envelope (tag 96, recipient bob) from alice (or, in ATEP-R, `controller`) whose inner envelope carries its attestations inline under the unprotected label `-70009` (an array of tag 98 envelopes, each embedded as a CBOR value). Inline attestations may carry their own `-70012` inclusion proof. The attestations' signer bundles are inline, so no `known_bundles` are needed.

`inputs.policy.trust` keys: `roots` (Agent IDs), `rules` (`[{claim, root?, max_age_days?}]`; `claim` may be a short name), `max_depth` (default 5, counts attestations in a chain including the claim attestation), `require_inclusion` (bool), `trusted_logs` (Agent IDs), `srl` (`{on_stale, on_missing}`, each `fail-closed` or `fail-open`; defaults `fail-closed` and `fail-open`), `atep_r` (bool).

Step 9 for each rule, with the signer of the data envelope as subject:

1. Candidates are the pooled attestations (inline in the envelope and its attestations, then `policy.attestations`) whose payload `subject` is the signer and whose `claim` equals the rule's claim.
2. Each candidate is verified as an envelope with steps 1 to 8 (`now` and the SRLs as for the outer envelope; replay checking off), it must be unencrypted with content type `application/atep-attestation+cbor`, its payload must pass the schema and claim rules, `issuer` must equal the signer, and `expires-at` minus `issued-at` must not exceed 400 days.
3. The issuer's SRL (the cached SRL whose `issuer` is the attestation's issuer) is looked up. Missing or stale SRLs follow `srl.on_missing` and `srl.on_stale`; with fail-open the result carries a warning. An SRL entry with the attestation's `id` rejects it.
4. If `require_inclusion`, the attestation's `-70012` proof must verify (see "Log vectors").
5. `max_age_days`: `now - issued-at` must not exceed `max_age_days * 86400`.
6. The issuer must be authorized for the claim: it is one of the roots (the rule's `root` if given), or it holds an `issuer-authority` attestation (same verification as above) whose `data.claims` lists the claim and whose issuer is in turn authorized for both `issuer-authority` and the claim. A chain may not repeat an issuer and may not use more than `max_depth` attestations.
7. The first candidate that passes everything satisfies the rule. If none does, the error of the first candidate is reported (or `claim_missing` when there are none). Among the alternatives of an ATEP-R class the error of the alternative that satisfied the most rules is reported.

Step 9 error codes (always step 9): `policy_invalid`, `claim_missing`, `claim_too_old`, `claim_data_mismatch`, `attestation_invalid` (the attestation envelope failed steps 1 to 8; the result has `cause: {step, error}`), `attestation_schema_invalid`, `attestation_issuer_mismatch`, `attestation_lifetime_exceeded`, `attestation_revoked`, `issuer_not_authorized`, `chain_broken`, `chain_cycle`, `chain_depth_exceeded`, `srl_unavailable`, `srl_stale`, `inclusion_proof_missing`, `inclusion_proof_invalid`, `checkpoint_untrusted`, `checkpoint_schema_invalid`.

Step 8 additionally consults every cached SRL: an identity entry (16 byte `id` is an attestation, 32 byte `id` is an Agent ID, always a compromised or retired identity) naming the signer with `revoked-at <= issued-at` rejects with `signer_revoked`. This applies to the data envelope and to every attestation verified at step 9.

A positive result adds to `expected`:

```
"claims": [ {"claim", "issuer", "root", "expires_at" (earliest in the chain),
             "chain": [ {"id", "claim", "subject", "issuer", "issued_at", "expires_at"}, ... ]} ],
"checkpoint": null or {"log", "tree_size", "root_hash", "timestamp"},
"warnings": [...]         only when non-empty
"command_class": "..."    only for envelopes with header -70014
```

`chain` starts with the claim attestation and continues with the `issuer-authority` attestations up to the root's delegation. `checkpoint` is the one with the latest timestamp used. A negative result is `{"ok": false, "step", "error", "cause"?}`.

## SRL vectors (M2)

`srl/*.cbor` is a tag 98 envelope with content type `application/atep-srl+cbor` signed by the issuer. The payload is a map with text keys `issuer` (Agent ID), `sequence` (uint), `issued-at` (uint), `next-update` (uint, later than `issued-at`) and `revoked`, an array of `{id, reason, revoked-at}`. `id` is 16 bytes (an attestation id) or 32 bytes (an Agent ID, an identity revocation); `reason` is text (`superseded`, `withdrawn`, `compromised` or any other).

Loading an SRL: verify the envelope with steps 1 to 8, require the SRL content type, validate the schema, require `issuer` equal to the signer, then apply the sequence rule against the cache (a lower `sequence` than the cached one is a rollback, the same `sequence` with different bytes is a conflict, identical bytes are accepted). A list is stale when `now >= next-update`.

`inputs`: `now`, `srl_policy.on_stale` (`fail-closed` or `fail-open`), `known_bundles` (empty), `cached_srl_hex` (an SRL already in the cache, or null). `expected`: `{ok: true, issuer, sequence, issued_at, next_update, stale, revoked: [{kind, id_hex or id, reason, revoked_at}], warnings?}` or `{ok: false, step, error}`.

| Vector | Result |
| --- | --- |
| srl-valid | ok, 2 entries |
| srl-stale-fail-open | ok, stale, warning |
| srl-stale-fail-closed | step 9 srl_stale |
| srl-bad-signature | step 4 mldsa_signature_invalid |
| srl-issuer-mismatch | step 9 srl_issuer_mismatch |
| srl-schema-invalid | step 9 srl_schema_invalid |
| srl-sequence-rollback | step 9 srl_rollback |
| srl-sequence-conflict | step 9 srl_sequence_conflict |

## Log vectors (M2)

A checkpoint is a tag 98 envelope with content type `application/atep-checkpoint+cbor` signed by the log, payload `{tree-size, root-hash (32 bytes), timestamp}`. An inclusion proof is carried in the unprotected header of an attestation under `-70012` as a map `{leaf-index, audit-path: [32 byte hashes], checkpoint: <the checkpoint envelope embedded as a CBOR value>}`.

The Merkle tree is RFC 9162: leaf hash `SHA-256(0x00 || leaf)`, node hash `SHA-256(0x01 || left || right)`, inclusion proof verification as in RFC 9162 section 2.1.3.2. The leaf of an attestation is its *submitted form*: the attestation envelope bytes with the `-70012` entry removed from the unprotected header (re-encoded deterministically), everything else unchanged.

Checking a proof: verify the checkpoint envelope (steps 1 to 8), require the checkpoint content type, require that its signer is in `trusted_logs`, validate the checkpoint schema, and check that the audit path leads from the leaf hash at `leaf-index` to `root-hash` for `tree-size`.

`inputs`: `now`, `check` (`checkpoint`: the `cbor` is a checkpoint envelope; `inclusion`: the `cbor` is an attestation carrying a proof), `trusted_logs`. `expected`: `{ok: true, checkpoint: {log, tree_size, root_hash, timestamp}}` or `{ok: false, step: 9, error, cause?}` with `inclusion_proof_missing`, `inclusion_proof_invalid`, `checkpoint_untrusted`, `checkpoint_schema_invalid`.

Vectors: `checkpoint-valid`, `checkpoint-untrusted-log`, `checkpoint-bad-signature`, `inclusion-valid` (leaf 3 of 5), `inclusion-valid-odd-tree` (leaf 6 of 7), `inclusion-wrong-audit-path`, `inclusion-altered-envelope`, `inclusion-missing-proof`, `inclusion-untrusted-log`.

## Log vectors (M3)

M3 adds 13 vectors to the `log` category (existing ones are unchanged). They exercise the RFC 9162 section 2.1.4 consistency proofs a monitor relies on and the split view rule of the gossip mechanism (spec section 9). The checker is `OfflineInclusion::check_consistency` and `check_split_view` in `atep-core`; the `log` service in `atep-log` and the monitor in `atep-monitor` call the same functions. The wire layouts are provisional (see [`docs/implementation-findings/rust-findings.md`](../docs/implementation-findings/rust-findings.md) 34).

A *consistency proof* is the map `{from, to, path}`: tree sizes as integers and `path` an array of 32 byte hashes (RFC 9162 section 2.1.4.1). Verification is RFC 9162 section 2.1.4.2, with two additions: a first tree size of 0 needs an empty path and the empty tree hash, and equal sizes need an empty path and equal roots.

The CBOR file of a `consistency` vector is the map `{old, new, proof}`: two checkpoint envelopes (tag 98 values embedded as CBOR values, as in the inclusion proof) and the consistency proof between them. The CBOR file of a `split-view` vector is the map `{a, b, proof?}`: two checkpoint envelopes claimed to come from one log and an optional proof. `inputs`: `now`, `check` (`consistency` or `split-view`), `trusted_logs`.

Checking `consistency`: verify both checkpoints as for `check: checkpoint` (steps 1 to 8, content type, trusted signer, schema), require the same signer, require `new.tree-size >= old.tree-size`, require `proof.from == old.tree-size` and `proof.to == new.tree-size`, then verify the proof from `old.root-hash` to `new.root-hash`. Any failure of the last four is `consistency_proof_invalid` at step 9.

Checking `split-view`: verify both checkpoints and require the same signer (else `consistency_proof_invalid`). Equal tree size: equal roots are fine, different roots are `split_view_detected`. Different sizes: a proof between the two sizes is required (`consistency_proof_invalid` when missing or when its sizes do not match); a proof that does not verify is `split_view_detected`, because two valid signatures of one log then cover histories that cannot both be append-only extensions of each other.

`expected`: `{ok: true, old: {...}, new: {...}}` (consistency) or `{ok: true, a: {...}, b: {...}}` (split-view) with the checkpoint objects of the M2 log vectors, or `{ok: false, step: 9, error, cause?}`.

| Vector | Check | Result |
| --- | --- | --- |
| consistency-valid | consistency | ok, sizes 3 to 8 |
| consistency-valid-power-of-two | consistency | ok, sizes 4 to 7 (old size is a power of two) |
| consistency-same-size | consistency | ok, size 5 twice, empty proof |
| consistency-invalid-path | consistency | consistency_proof_invalid, first path hash altered |
| consistency-truncated-path | consistency | consistency_proof_invalid, last path hash removed |
| consistency-rewritten-history | consistency | consistency_proof_invalid, leaf 1 rewritten after the size 3 checkpoint, new checkpoint and proof built over the rewritten tree |
| consistency-shrinking-tree | consistency | consistency_proof_invalid, newer checkpoint is smaller |
| consistency-untrusted-log | consistency | checkpoint_untrusted |
| checkpoint-schema-invalid | checkpoint | checkpoint_schema_invalid, valid signature, payload lacks `root-hash` |
| split-view-none | split-view | ok, sizes 5 and 8 with a valid proof |
| split-view-same-size | split-view | split_view_detected, two roots for size 6 |
| split-view-failed-consistency | split-view | split_view_detected, size 5 and size 8 from different histories |
| split-view-missing-proof | split-view | consistency_proof_invalid, sizes differ and there is no proof |

The `checkpoint-valid` and `checkpoint-bad-signature` vectors of M2 cover the valid checkpoint and bad signature cases. `crosscheck.py` independently re-checks the consistency proof and split view vectors with its own RFC 9162 section 2.1.4.2 verifier and the Ed25519 signatures of the checkpoints; the ML-DSA-65 signatures rest on the Rust checker.

## ATEP-R vectors (M2)

Verification vectors with `inputs.policy.trust.atep_r = true` and roots `root` and `certifier`. The data envelope carries the protected header `-70014` (`command-class`, text). With ATEP-R enabled step 1 additionally requires: the envelope is encrypted (`atep_r_unencrypted`), the header is present (`missing_command_class`) and is one of `telemetry`, `sensor`, `coordination`, `motion`, `actuation`, `safety`, `maintenance` (`unknown_command_class`). Step 9 then requires, in addition to any `rules`:

| Class | Required (alternatives separated by `or`) | SRL stale or missing |
| --- | --- | --- |
| telemetry | fleet-member | warning |
| sensor | fleet-member and sensor-source | warning |
| coordination | fleet-member | warning |
| motion | fleet-controller, or fleet-member and peer-motion whose `data.peers` (array of Agent IDs) contains the receiver | fail closed |
| actuation | fleet-controller and safety-certified | fail closed |
| safety, e-stop | safety-authority, or fleet-member and safety-certified; attestation expiry is ignored | warning |
| safety, other | safety-authority | fail closed |
| maintenance | maintenance-authority | fail closed |

An e-stop is a `safety` payload that is a CBOR map with `command` equal to `"e-stop"` (the spec does not define how an e-stop is recognized, see the Rust implementation findings). The e-stop relaxation covers attestation expiry only: signatures, SRL revocation, authority chains and the 400 day maximum are still enforced, and the envelope's own `expires-at` is still checked at step 5. The "fail closed" column applies to a stale or missing SRL for every issuer in the chain; for the other classes it is a warning (`telemetry` MAY continue, spec section 17). The claims are the robotics set under `https://atep.dev/claims/robotics/`; `fleet-member` and `sensor-source` are issued by the controller (who holds `issuer-authority` from the root), `fleet-controller`, `safety-authority` and `maintenance-authority` by the root, `safety-certified` by the certifier.

Positive: `telemetry-fleet-member`, `telemetry-stale-srl-continues`, `sensor-fleet-member-and-sensor-source`, `coordination-fleet-member`, `motion-from-fleet-controller`, `motion-from-member-with-peer-motion`, `actuation-controller-and-safety-certified`, `safety-geofence-from-safety-authority`, `estop-from-certified-fleet-member`, `estop-with-expired-claims`, `estop-stale-srl-continues`, `maintenance-from-maintenance-authority`.

Negative: `telemetry-no-fleet-member`, `sensor-missing-sensor-source`, `coordination-expired-fleet-member`, `motion-member-without-peer-motion`, `motion-peer-motion-lists-other-peer`, `motion-stale-srl-fails-closed`, `motion-sender-compromised` (step 8), `motion-fleet-controller-revoked`, `actuation-without-safety-certified`, `safety-geofence-from-certified-member`, `estop-from-uncertified-fleet-member`, `estop-safety-certified-revoked`, `maintenance-from-fleet-member`, `missing-command-class`, `unknown-command-class`, `unencrypted-atep-r-envelope`. Each description names the expected step. Motion, actuation, maintenance and geofence vectors carry fresh SRLs for the chain issuers because a missing SRL also fails closed for them.

## M2 cross-check coverage

`crosscheck.py` independently re-checks: the Ed25519 signature, agent ID binding, payload digest and payload schema of `attestation/operator-90-days` and `srl/srl-valid`; the signature, schema and RFC 9162 inclusion proof (leaf hash over the submitted form, audit path, tree size and root) of `log/inclusion-valid`, including that a changed leaf fails, and the M3 consistency proofs (valid, altered, truncated and rewritten-history paths) and split view pairs. It also uses its own deterministic CBOR encoder to re-create the submitted form, which checks the encoding rules. Not independently cross-checked: ML-DSA-65 signatures, the chain walking and authorization rules, SRL sequence and staleness handling, the ATEP-R table, and the JSON view. Those rest on the Rust checker (`atep-vectors check`) until a second implementation exists (milestone M4).

## JSON view

Informational rendering of the CBOR: maps become objects with integer labels replaced by names (`alg`, `kid`, `iv`, `content-type`, `signer`, `issued-at`, `expires-at`, `nonce`, `payload-digest`, `suite`, `atep-version`, `signer-bundle`, `ephemeral-key`, `kem-ciphertext`, and for keys `kty`, `alg`, `crv`, `x`, `pub`), byte strings become unpadded base64url, algorithm numbers become names (`EdDSA`, `ML-DSA-65`, `A256GCM`, `ECDH-ES+HKDF-256`, `ML-KEM-768`, `ATEP-1-HYBRID-KEM`), and a CBOR payload of an `+cbor` content type is also shown decoded under `payload-decoded`. Signatures are only ever computed over the CBOR form.

## Provisional values

All of these are private-use values pending IANA registration (spec section 5): header labels -70001 to -70007, -70014 (command-class), -70008 signer-bundle, -70009 attestations, -70012 inclusion-proof, -70013 kem-ciphertext; alg -49 ML-DSA-65, -70010 ML-KEM-768, -70011 ATEP-1 hybrid KEM; kty 7 AKP; the media types of the three trust documents. See [`../docs/implementation-findings/rust-findings.md`](../docs/implementation-findings/rust-findings.md) for the open questions behind the M2 choices (issuer-authority layout, e-stop recognition, leaf hash, SRL boundary and others).

## Draft 04 addendum: `retired` and `successor`

200 vectors in all: the 140 above (unchanged, same order and bytes in `manifest.json`) and 60 new ones, appended to the manifest in this order. Every case of the section 12 tables ("Cases for `retired` and `successor`") has a vector whose name begins with the case number (`rt01` to `rt31`, `su01` to `su26`); a case with two parts (RT6, RT31, SU14) has two vectors, `a` and `b`. The descriptions in the `.expected.json` files restate the case. `RETIRED-SUCCESSOR-NOTES.md` lists what an implementation has to do to pass them.

| Category | Vectors | Cases |
| --- | --- | --- |
| `retired-positive` | 15 | RT1, RT5, RT6a, RT7, RT8, RT9, RT12, RT15, RT17, RT18, RT19, RT21, RT23, RT27, RT29 |
| `retired-negative` | 13 | RT2, RT3, RT4, RT6b, RT10, RT11, RT13, RT14, RT16, RT20, RT22, RT26, RT28 |
| `successor-positive` | 9 | SU1, SU5, SU10, SU12, SU17, SU19, SU21, SU23, SU24 |
| `successor-negative` | 16 | SU2, SU3, SU4, SU6, SU7, SU8, SU9, SU11, SU13, SU14a, SU14b, SU15, SU16, SU18, SU20, SU22 |
| `srl-context` | 2 | RT24, RT25 |
| `log-admission` | 4 | RT30, RT31a, RT31b, SU26 |
| `monitor` | 1 | SU25 |

**Identities.** New signing-only identities with the usual seeds (`SHA-256("ATEP-vectors-v1/<name>/<field>")`, fields `ed25519` and `mldsa65`), named as in the tables: `x` (the identity that retires), `y` (any other identity), `o0`, `o` and `s` (an old identity, its successor, and the successor's successor, where `s` is the signer in the SU cases), `i` and `p` (root issuers). `bob` is the recipient of every data envelope and `log` is the log. The key bundles travel inline in every envelope, so a verifier needs no seeds except `recipient_seeds`.

**`retired-*` and `successor-*`** are verification vectors in the format of "Verification vectors" and "Trust policy evaluation" above: the CBOR file is an encrypted data envelope to bob (`E(t)` of the tables: signed with `issued-at` t, no `expires-at`, its attestations inline under `-70009`), except RT18, RT19 and RT20, where it is the unencrypted `retired` attestation under test and `recipient_seeds` is absent. `inputs.policy` carries the verifier context. Two members matter here:

* `attestations` is the **local attestation store**. It is the third pool source of step 9 and, new in Draft 04, the place where step 8 looks for valid `retirements` (spec section 7), also when there is no `trust` policy and for the step 8 of every attestation verified at step 9. The `R` of the tables is an entry of this list unless a case says it travels inline.
* `trust` may set the new member `follow_succession` (boolean, default false). Every other member keeps its meaning.

`revocations` (`{id, reason, revoked_at}`) are the directly supplied revocations of step 8, and `srls` the cached SRLs, as before. The SRLs are loaded one after the other **in the verifier's own context**: each list is verified with steps 1 to 8 against the lists loaded before it, `revocations` and `attestations`. A list that fails to load makes the vector invalid; no vector supplies one that does.

**`srl-context`** (RT24, RT25) uses the inputs of the `srl` vectors (`now`, `srl_policy`, `known_bundles`, `cached_srl_hex`) plus the optional `attestations` (the local store, hex) and `revocations` (as in `inputs.policy`). The CBOR file is the SRL to load. The result is the one of the `srl` vectors: `{ok: true, issuer, sequence, ...}` or `{ok: false, step, error}`. `cached_srl_hex`, when present, is loaded first (in the same context), then the CBOR file; for RT25 both are the same bytes, which must be accepted both times.

**`log-admission`** (RT30, RT31, SU26): the CBOR file is the submission. `inputs`: `now`, `log` (the log's Agent ID), `max_envelope_bytes` and `logged`, the submitted forms (hex) of the documents the log holds, in order; each of them is admitted first with the same rules at `now`. The rules are those of section 9 ("Admission") with the claim vocabulary of the 14 core claim types. `expected` is `{ok: true, document: "attestation"}` or `{ok: false, refusal: "<reason>"}`, with `step` and `error` added for `verification_failed` (the failing step 1 to 8 of the submitted form and its code). The log uses the identity entries of the SRLs it holds as the revocations of step 8 and the `retired` attestations it holds as the local attestation store.

**`monitor`** (SU25): the CBOR file is the map `{"entries": [envelope, ...]}`, the entries of a log in log order (submitted forms, embedded as CBOR values); entry 0 is the first of the list, whereas a real log also holds its policy entry first. `inputs`: `now`, `check` (`alerts`). `expected` is `{alerts: [{alert, entry, issuer, subject}]}` in the order of the entries. The only alert of these vectors is `successor_chain`: a `successor` attestation whose issuer is the subject of another `successor` attestation of the list; `entry` is the index of the link whose issuer is that subject (the later link of the chain), `issuer` and `subject` those of that attestation. Each entry is verified as of its own `issued-at` with its inline bundle, as the monitor does.

**Timeline.** `now` is 1800000000 as always. The `retired` attestation `R` of X has `issued-at` 1799990000 and `expires-at` 1830000000; the data envelope `E(t)` has `issued-at` t; in the SU cases `E` is issued at 1799999000, `A_O` at 1799000000 and `SUC` at 1799500000 (both expire at 1830000000). The cached SRL of a retired or revoked issuer is issued before the instant it is revoked from (a retired issuer cannot publish later, RT24): that of X at 1799980000 and that of O at 1799400000, with `next-update` 1800082800 unless the case makes it stale (the SRL of O0 in SU8 is issued at 1799300000). Other SRLs are issued at 1799996400 as in the chain vectors. Every SRL names one unrelated attestation id and nothing else unless a case says so.

The Rust reference passes all 200 with `cargo run --release -p atep-core --bin atep-vectors -- check ../vectors`. The `log-admission` and `monitor` vectors are also run against the real log (`atep-log/tests/retired_successor.rs`) and monitor (`atep-monitor/tests/retired_successor.rs`). `crosscheck.py` does not cover the new categories; they rest on the Rust checker until the Python and JavaScript implementations pass them.

Layout: one directory per category under `vectors/`, three files per vector as above. Formats, in short (the notes file has the rules):

* **Object under test in JSON** (`require-anchor`, `domain-binding`, and `chain-id`, whose text is a CBOR text string): `inputs` carries the value (`inputs.policy`, `inputs.fixture`, `inputs.id`) and the `.cbor` file is its deterministic CBOR encoding, so that the manifest still pins every vector by the hash of a `.cbor` file. The `.json` file is the same value. An implementation reads the value from `.expected.json`.
* **`checkpoint-hash`**: the CBOR file is a checkpoint envelope; `inputs` `{now, trusted_logs}` as for `log` vectors with `check: checkpoint`; `expected` the checkpoint result plus `checkpoint_hash` and `payload_hex`, or a rejection.
* **`anchor-record`**: the CBOR file is the record payload bytes, possibly not strict deterministic CBOR (then its `.json` is `{"not_strict_cbor": true, "hex": ...}`); `inputs` `{check: "anchor-record"}`; `expected` `{ok: true, record: {checkpoint_hash, chain_id, transaction_id, block_height, anchored_at}}` or `{ok: false, error: "anchor_record_invalid"}`.
* **`chain-id`**: `inputs` `{check: "chain-id", id}`; `expected` `{ok: true, kind: "registered" | "extension"}` or `{ok: false}`.
* **`anchor-envelope`**: the CBOR file is a tag 98 envelope; `inputs` `{now, log, checkpoint_hash_hex}`; `expected` `{ok: true, log, record}` or `{ok: false, step, error}` with the new step 9 codes `anchor_content_type_invalid`, `anchor_schema_invalid`, `anchor_log_mismatch`, `anchor_checkpoint_mismatch` (steps 1 to 8 are reported as they are).
* **`anchor-media-type`, `anchor-not-supported`**: verification vectors in the format of "Verification vectors" above (`inputs.policy`, `expected` the section 10 result).
* **`require-anchor`**: `inputs` `{check: "require-anchor", policy}`; `expected` `{ok: true, require_anchor: [{log, chain, max_age_days | max_age_hours}]}` or `{ok: false, error: "policy_invalid"}` (a configuration error, no step).
* **`registry-endpoint`**: the format of `log-admission` (the CBOR file is the submitted attestation), `logged` empty.
* **`domain-binding`**: `inputs` `{check: "domain-binding", fixture}` with the fetcher's answers by name, the Agent ID asked about and the options; `expected` `{well_known, dns, outcome, queried}`. No network is involved.

Seeds and identities are as above (`log`, `mallory`, `alice`, `bob`, `carol`, `root`; the reference time is `now = 1800000000`; the checkpoint of an anchoring vector has timestamp 1799996400).

The Rust reference passes all 436 with `cargo run --release -p atep-core --bin atep-vectors -- check ../vectors`; the `registry-endpoint` vectors are also run against the real log (`atep-log/tests/discovery.rs`). `crosscheck.py` does not cover the new categories.
