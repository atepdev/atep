# CDDL notes

`atep.cddl` formalizes [Draft 08](../ATEP-Specification-Draft-08.md) (Drafts 07 and 08 carry the content of the internal Draft 06 as far as this file is concerned and change no rule of it) and matches the 437 vectors in `vectors/` (validated, see "Validation status" below). Draft 06 changes no rule of this file, only its comments (the anchor record integers are 0 to 2^63-1 by the encoding rules, the extension `kind` rule is looser than the `chain-id` rule, the Draft number and the vector count); the `chain-id` and `agents` fixes found by the validator are described at the end. Draft 05 changes no wire format of an envelope, attestation, SRL or checkpoint and no vector. Its changes to this file are comments (the exemption of step 8 is decided on shape, so a malformed `retired` attestation of the signer is exempt at step 8 and fails the schema check of its consumer) and three small rules at the end for the document of a `monitor` vector (`monitor-input`, `monitor-expected`, `successor-chain-alert`). The other new vector formats are JSON test files and are described in spec section 12, not here: `srl-context` (`attestations` and `revocations` at the top level of `inputs`), `log-admission` (`logged`, `max_envelope_bytes`) and the `retired-*` and `successor-*` verification vectors (the local attestation store is `inputs.policy.attestations`). A policy that does not parse is the configuration error `policy_invalid` (spec section 7), and `trust-policy` below is the grammar it is checked against. Relative to Draft 03, Draft 04 added, and the CDDL still covers:

- The anchor record (section 9): the map `{checkpoint-hash, chain-id, transaction-id, block-height?, anchored-at}`, the payload of an envelope with content type `application/atep-anchor+cbor` signed by the log, and the `chain-id` rule (five registered ids, extension form `x-<name>`; the registered ids are listed in a comment because CDDL would have to grow with every registration). The checkpoint hash is `SHA-256` of the encoded `checkpoint` map and is described in a comment.
- The claim data layouts: `registry-endpoint-data` and `endpoint-kind` (section 7, new), and `retired-data` and `successor-data` (now normative, section 7, "Retirement and succession"). CDDL cannot say that a `retired` attestation has `subject` equal to `issuer`, that a `successor` has `subject` different from `issuer`, or the URL rules of `registry-endpoint`; comments in the file state them and the spec text is normative.
- The closed core claim list, now 14 types (`core-claim` gains `registry-endpoint`).
- Two new members of the trust policy file (JSON): `require_anchor` (an array of `anchor-rule`, each with `log`, `chain` and exactly one of `max_age_days` and `max_age_hours`; not evaluable in Draft 04, so step 9 fails closed with `anchor_not_supported`) and `follow_succession` (boolean, default false).
- The well-known domain document (`well-known-document`, section 4). The TXT record at `_atep.<domain>` is not CBOR or JSON, so it is described as ABNF in comments here and normatively in section 4:

  ```
  record   = "v=atep1" *( 1*SP term )
  term     = id-term / srl-term / ext-term
  id-term  = "id=" agent-id
  srl-term = "srl=" https-url
  ```

  The domain records are JSON and DNS text, not ATEP CBOR, and nothing in them is signed. A JSON Schema for the well-known document, if a tool needs one, is:

  ```json
  {
    "type": "object",
    "required": ["version", "agents"],
    "properties": {
      "version": { "const": 1 },
      "agents": { "type": "array", "maxItems": 1024 },
      "domain": { "type": "string" },
      "srl-url": { "type": "string" },
      "updated": { "type": "integer", "minimum": 0 }
    },
    "additionalProperties": true
  }
  ```

  (An `agents` entry that is not an Agent ID is ignored by the reader, which a schema cannot express; `domain`, when present, must equal the name the document was fetched for.)

Not covered by CDDL, because the JSON of the log API is described by the OpenAPI document that `GET /openapi.json` serves (reference copy: `rust/docs/openapi.json`): the `checkpoint-hash` and `anchors` members of the checkpoint objects, the claim-type resolver documents and the claim-type directory rows. The CBOR documents are the normative part.

Carried from Draft 03: the claim data layouts of section 7 (`issuer-authority-data`, `domain-control-data`, `peer-motion-data`), the SRL entry reasons including `retired` and the meaning of `id` by length (section 8), the consistency proof, the `{old, new, proof}` consistency check document and the `{a, b, proof?}` split view document (section 9), the log policy `data` map, the trust policy file format of section 7 with its defaults, and the verification result shapes of section 10, which the vectors compare.

Still provisional (private-use values pending IANA): labels -70001 to -70014, alg -49 (ML-DSA-65), -70010 (ML-KEM-768), -70011 (hybrid KEM recipient), kty 7 (AKP), the SRL, checkpoint and anchor media types, and the log policy claim URI `https://atep.dev/log/policy`.

What CDDL cannot say, and the spec text covers instead: deterministic CBOR encoding (section 5, encoding rules), `kid` equals `signer` (step 3), the signer bundle hashes to the Agent ID (step 3), `expires-at` present for attestations and the encryption rule (step 1), the Sig_structure signed by each signature, the AES-GCM AAD, attestation `issuer` equals the signer, the evidence requirement of `audited` and `safety-certified`, the 400 day lifetime limit, `next-update` later than `issued-at`, the Merkle leaf (`SHA-256(0x00 || submitted form)`), the checkpoint hash, the rules of `retired` and `successor`, an anchor record signed by the log for a checkpoint it signed, and every check of the verification algorithm. The URI type is a text string whose scheme rule is stated in the comment on `uri`.

Validation status: `atep.cddl` is machine-validated against the vectors with the Rust `cddl` crate, version 0.10.7 (`cargo install --locked --version 0.10.7 cddl`; it needs a C toolchain to link, which CI has; on a box without one a linker shim works). The driver is `scripts/ci/validate-cddl.mjs` (Node, no dependencies), the table is `scripts/ci/cddl-map.json` (vector pattern to rule, expected pass or fail, with a reason for every expected failure) and CI runs it as the job `cddl`. Run it locally with `cddl` on `PATH` (or `CDDL=/path/to/cddl`) and `node scripts/ci/validate-cddl.mjs`; `--verbose` prints the tool's message for every expected failure and `--list` prints every check.

What it covers. The tool validates CBOR directly, including tags, integer map keys, `.size`, `.cbor` (so the protected headers and the COSE signature headers inside their byte strings are checked), `.regexp`, `.ge` and group choices. All 437 vectors are covered, 354 by their own `.cbor` file and the other 83 (`domain-binding`) through their fixtures:

- Every `.cbor` file but those of `domain-binding` against its rule: the `identity` files against `key-bundle` (10), the tag 98 and tag 96 files against `signed-envelope` (114, of which 4 expected failures) and `encrypted-envelope` (123), the consistency and split view documents (8 and 4), the monitor input (1), the 36 `anchor-record` files against `anchor-record`, the 30 `chain-id` texts against `chain-id`, and the 27 `require-anchor` policies (deterministic CBOR of the policy JSON) against `trust-policy`. For `chain-id`, `require-anchor` and `anchor-record` the verdict comes from the vector itself: the schema must accept exactly the vectors whose `expected.ok` is true (see the exceptions below).
- The payloads of the envelopes that carry a real trust document (outer files of `attestation`, `srl`, `log`, `retired-*`, `srl-context`, `log-admission`, `anchor-media-type`, `anchor-envelope`, `checkpoint-hash` and `registry-endpoint`, and every envelope in `inputs`: 89 attestations of the local store, 204 SRLs, and the cached SRL, `attestations` and `logged` lists) against `attestation`, `srl`, `checkpoint` or `anchor-record`, and the `data` map of each attestation against the layout of its claim (`issuer-authority-data`, `retired-data`, `successor-data`, and `registry-endpoint-data` for the 26 `registry-endpoint` vectors; `domain-control-data` and `peer-motion-data` have no attestation in a vector).
- The JSON of the vectors: `inputs.policy.trust` against `trust-policy`, `inputs.policy` of `require-anchor` and `inputs.id` of `chain-id` against `trust-policy` and `chain-id` (same verdicts as their `.cbor`), `expected` against `verify-ok` or `verify-rejected`, the monitor result against `monitor-expected`, and the well-known `body` of every `domain-binding` fixture whose expected state is `listed` or `not-listed` (23) against `well-known-document`.
- 116 mutation checks (`mutations` in the map): documents derived from a vector or written out, whose verdict is known by construction (a size off by one, a missing or extra key, a wrong tag, a wrong type, either signature order, an unknown label). They show that the tool really enforces what the schema says, and they remain only for formats without a vector: `log-policy-data`, `peer-motion-data`, `domain-control-data`, `issuer-authority-data` negatives, the invalid well-known documents (a `domain-binding` vector says a body is invalid but not which schema rule it breaks) and members of `trust-policy` other than `require_anchor`.

Expected failures, each marked in the map with its reason: the four envelopes that are schema-invalid by design (`verify-negative` `missing-pq-signature` and `missing-classical-signature`, `unknown-suite`, `unsupported-version`); the payloads of `srl-schema-invalid`, `checkpoint-schema-invalid`, `checkpoint-hash` `reject-missing-root-hash` and `reject-unknown-payload-key`, `anchor-envelope` `payload-unknown-key`, `payload-unregistered-chain-id`, `payload-not-a-map` and `wrong-content-type`, and `anchor-media-type` `bare-anchor-envelope-garbage-payload-accepted` (a text payload under the anchor media type, accepted by the core verifier, which checks the label only); the `retired` data of `rt08`; the 10 `registry-endpoint` vectors refused for their `url` or `kind` layout; and, through `expected.ok`, the invalid ids, anchor records and policies of `chain-id` (20), `anchor-record` (26) and `require-anchor` (26 failing policies, counted in `trust-policy`). Exceptions in the other direction, vectors that the schema accepts although the implementation refuses them (marked `pass` in the map): the 8 `registry-endpoint` vectors refused for a URL rule (scheme, host, credentials, whitespace, length: CDDL types `url` as text and the rules are stated in comments), `require-anchor` `invalid-log-malformed` (the Agent ID text form is not expressible), and the 5 `anchor-record` vectors that are not strict deterministic CBOR on purpose (unsorted keys, duplicate key, indefinite length, non shortest head, trailing bytes; the decoded value matches the schema and the encoding rules are outside CDDL).

What it does not cover:

- `domain-binding`: the `.cbor` of each vector is the deterministic CBOR of its JSON fixture (a test format, not a protocol document) and has no rule; only the well-known bodies are validated, and the other 60 vectors (invalid documents, unavailable sources, DNS only) have nothing the schema can judge. The same holds for the `.cbor` of `require-anchor` and `chain-id`, which are validated as the JSON values they encode.
- The payloads of the tag 96 vectors (`chain-*`, `atep-r-*`, `retired-*`, `successor-*`, `anchor-not-supported` and the `verify-*` data envelopes) are not visible without the recipient key, so the inner signed envelope, its inline attestations and its payload are not checked, only the outer tag 96 structure. This includes `chain-negative/attestation-schema-invalid`. The attestations, SRLs and logged envelopes that the vectors list in `inputs` are checked, and they are the same documents.
- The payloads of the `signing` and `verify-*` vectors are the generic test payload `{"vector", "note"}` under a trust document content type (to exercise the encryption rule), so they are not schema-valid trust documents and are not checked against `attestation` or `srl`.
- Everything in the list above of what CDDL cannot say (deterministic encoding, signatures, `kid` against `signer`, `issuer` against the signer, evidence for `audited`, the 400 day limit, `next-update` after `issued-at`, `retired` and `successor` subject rules, URL rules, hashes) is not checked by a schema and is covered by the verification vectors and the implementations.
- The tool decodes CBOR into a tree, so it does not check that the encoding is deterministic or even shortest form. The log policy data has no vector and is checked only by the mutation checks above, not against output of an implementation.
- Two defects of `cddl` 0.10.7 are worked around in the copy of the schema that the tool reads (`tool_workarounds` in the map, applied by the script and not to this file). It rejects every entry matched by a wildcard member whose key is a type choice, so `* (int / tstr) => any` in `protected-header` and `unprotected-header` is replaced by `* any => any` for the run (the tool therefore also accepts a byte string, boolean or null key in those two maps, which the schema forbids). And it matches `.regexp` at the start of the string only, so an end anchor `$` is added to the two patterns of `extension-chain-id` and `endpoint-kind` for the run (the schema keeps the RFC 8610 whole-string form). It also cannot chain `.size` with `.regexp` or apply `.regexp` to a parenthesized type, which is why the length limit of `extension-chain-id` (3 to 64 bytes) is written into its pattern. A schema edit that stops matching the workaround makes the script fail.
- The JSON of the log API (OpenAPI), the ABNF of the TXT record and the other JSON test files are not checked by this tool.

Found while validating the first 200 vectors: the `signatures` member of `signed-envelope` required the EdDSA entry first, although section 5 says verifiers accept either order, so it is now `[classical-sig, pq-sig] / [pq-sig, classical-sig]` (exactly one of each). No vector orders them otherwise, and none of the 200 vectors changed. The reference log's test `layouts_agree_with_the_spec_cddl` compares the first line of each claim data rule with this file and checks that every core claim URI of the code appears in `core-claim`. This replaces the earlier hand transcription (41 vectors, no validator), the npm `cddl` package (it does not parse integer map keys) and the open item of spec section 13 for the CDDL file.

Found while validating the Draft 05 anchoring and discovery vectors: `chain-id` is now the choice of the five registered ids and `extension-chain-id` (`x-` plus a name of lowercase letters, digits and hyphens that neither begins nor ends with a hyphen, at most 64 bytes in all), because the old `tstr .size (1..64)` accepted every id the `chain-id` vectors refuse; and `agents` of `well-known-document` is `[* any]`, because the vectors `wk-junk-entries-are-ignored` and `wk-only-junk-entries` carry non-text entries that the reader ignores (the JSON Schema earlier in this file was changed the same way).
