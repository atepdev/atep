Robots from different vendors can trust each other with ATEP

AIRAD LABS creates and stewards ATEP, the Autonomy Trust Envelope Protocol: an open, quantum-safe way for a robot or AI agent to prove who sent a command, that it was not altered, and that the sender is certified, across vendors, over any network, and even with no connection at all. The protocol and its reference code are free and open. We plan to offer certification, a hosted registry and the ATEP Fleet Console for operators; those services are not yet available.

Run the demo: three simulated robots exchange real encrypted envelopes, one is revoked mid-run and refused at the named step, and the fleet carries on. See products for what is planned and why ATEP for the reasoning.

How do robots from different vendors trust each other?

They verify each other's messages against rules the receiver chooses. Each message is wrapped in an ATEP envelope that is signed by the sender, encrypted to the receiver, and carries attestations from third parties such as a safety certifier. The receiver checks the signature, checks that the attestations chain to an issuer it has chosen to trust, and checks the issuer's signed revocation list, all offline, in milliseconds. No vendor has to trust another vendor; each trusts the issuers named in its own policy.

How do I secure multi-vendor robot fleet communication?

Put an ATEP envelope on every command and report, whatever carrier you use (ROS 2, MQTT, HTTP or MCP). The ATEP-R robotics profile requires end-to-end encryption and tags every message with one of seven command classes (telemetry, sensor, coordination, motion, actuation, safety, maintenance), each with a minimum claim the sender must hold. A relay or broker sees only ciphertext, and a command from a sender without the right claim is refused.

What is quantum-safe robot command authentication?

Authentication designed so that signatures remain trustworthy if large quantum computers arrive. ATEP signs every envelope twice, once with Ed25519 and once with the NIST post-quantum standard ML-DSA-65, and encrypts with X25519 plus ML-KEM-768. Both signatures must verify, so stripping the post-quantum signature fails. Quantum-safe here means finalized NIST standards in a hybrid construction; the code has not had an independent security audit. This matters because safety certifications and incident records signed today must stay valid for the life of the machine.

Where things stand. The specification is a working draft. Reference implementations in Rust, JavaScript and Python pass the shared test vectors they can run (all 436 for Rust, 431 for JavaScript and Python, which skip the five for a log and a monitor), and a transparency log and monitor are implemented. No functional package is published to a package registry yet (placeholder names with no code are reserved on crates.io, npm and PyPI), there has been no external security audit, no certification has been issued, and there are no customers to name.
