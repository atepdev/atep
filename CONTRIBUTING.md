# Contributing to ATEP

Thank you for looking. ATEP is a security protocol with three implementations that must agree byte for byte, so contributions are held to a few firm rules. Participation is covered by the [Code of Conduct](CODE_OF_CONDUCT.md). Vulnerabilities do not go through public issues: see [SECURITY.md](SECURITY.md).

## Licensing, no CLA

There is no contributor license agreement. Contributions are accepted under the license of the part of the repository they touch, inbound equal to outbound: code (Rust, JavaScript, Python, examples, demo, scripts, site) under Apache-2.0 ([LICENSE](LICENSE)), and the specification text and CDDL schemas under CC BY 4.0 ([LICENSE-SPEC.md](LICENSE-SPEC.md)). By opening a pull request you state that you have the right to contribute the material under those terms.

## The rules

1. **Vectors are authoritative.** The 443 vectors in `vectors/` define behavior. If the spec text and a vector disagree, the vector wins and the spec is amended to follow it. Never change a vector to make a test pass. Vectors are generated by `rust/atep-core` from fixed seeds and regenerating must give identical bytes (CI checks this). A change that needs a vector change needs a spec change first, linked in the pull request.
2. **The three implementations must stay in agreement.** Rust, `@atep/core` (the same Rust compiled to WASM) and Python must give identical bytes for identity, signing, encryption and attestation vectors and identical accept or reject, step and error code for the rest. If you change `rust/atep-core`, rebuild `js/` and run all three suites. Disagreement between them is the signal that the spec is underspecified: record it as a finding, do not paper over it.
3. **Python stays independent.** `python/atep_py` is built only from the spec and the vectors, as an interoperability test. Do not port code from `rust/` into it, and do not read `rust/` when changing it. Divergences between the spec text and what the vectors needed go in `docs/implementation-findings/python-findings.md`.
4. **Honest claims.** Do not write that something is published, certified, audited, deployed, registered with IANA or used by customers unless it is. Provisional media types, labels and algorithm identifiers stay called provisional.
5. **No em dashes or en dashes** in any file (code comments, docs, UI copy, commit messages). `scripts/ci/no-em-dashes.sh` checks em dashes.
6. **No frameworks in the demo, examples or site.** Plain HTML, CSS and ES modules, no build step for pages. `@atep/core` has no runtime dependencies. Python uses only the standard library.
7. **No custom cryptography.** Only the RustCrypto crates already in use; secrets are zeroized; rejection is a value with a step number and a stable error code, never a panic.

### Design commitments are contribution constraints

Section 16 of the specification is normative and binds contributions. A change will not be accepted if it adds, for example, a composite trust score or ranking, a claim type about a natural person, a mandatory root, log or registry, reputation in the core, an API that lists an agent's interactions, a way to submit agent-to-agent envelopes to a log, or any dependency on a blockchain, token or on-chain lookup. Optional anchoring lives only in log operator hooks.

## Building and testing each component

Any Rust build needs a C toolchain (`cc` as linker; on Debian or Ubuntu, `sudo apt install build-essential`).

| Component | Directory | Commands |
| --- | --- | --- |
| Rust workspace | `rust/` | `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --workspace` |
| Vectors, Rust check | `rust/` | `cargo run --release -p atep-core --bin atep-vectors -- check ../vectors` (expects `all 443 vectors pass`) |
| Vectors, regenerate | `rust/` | `cargo run -p atep-core --bin atep-vectors -- generate ../vectors`, only when the spec changes a vector; the result must be committed and reproducible |
| npm package | `js/` | needs the `wasm32-unknown-unknown` target and `wasm-bindgen-cli` 0.2.129 (see `js/README.md`); `npm ci` in the repository root (npm workspaces), `npm run build -w js`, `npm test -w js` |
| Python | `python/` | `python3 -m unittest`; `python3 -m atep_py.vectors check ../vectors` (Python 3.8 compatible) |
| MCP server | `mcp/` | `npm test -w mcp` from the root (needs `js/dist`; runs against the local `@atep/core`) |
| Examples | `examples/`, `examples/mqtt/` | `npm test -w examples` and `npm test -w examples/mqtt` from the root (need `js/dist`); ROS 2 example: `python3 -m unittest discover -s tests -v` in `examples/ros2` |
| Demo | `demo/` | `node demo/selftest.mjs`; `node demo/serve.mjs`; after any change in `demo/`, `node site/build-demo.mjs` refreshes the hosted copy in `site/atep.dev/demo/` (commit it) |
| Site and repository checks | root | `node site/build-llms-full.mjs`, `node site/build-demo.mjs --check`, `node site/check.mjs`, `bash scripts/ci/no-em-dashes.sh`, `bash scripts/ci/no-local-paths.sh`, `node scripts/ci/vector-counts.mjs`, `node scripts/ci/check-md-links.mjs`, `scripts/release/check-versions.sh` |

Releases: [`docs/RELEASING.md`](docs/RELEASING.md) (owner steps, trusted publishing) and [`docs/VERSIONING.md`](docs/VERSIONING.md). Packaging checks: `cargo publish --dry-run -p atep-core --allow-dirty` in `rust/`, `npm pack --dry-run -w js -w mcp` in the root, `python -m build` and `twine check` in `python/` (from a copy, so build directories stay out of the tree).

The workflows in `.github/workflows/` run all of this; see `.github/workflows/README.md`.

## Proposing a change to the specification

1. Open an issue using the "Specification issue" template: the draft and section, the problem (quote the text, say which readings are possible), and a proposed rule.
2. Say which vector (new or existing) would pin the behavior down. Specification changes that alter behavior come with vectors and with the three implementations updated, in one pull request or a linked set.
3. Once a draft is released it is not edited in place: a change is a new draft file in `spec/` with an entry in the revision history (Appendix A). Typo fixes and clarifications that change no rule can be made to the current draft in a pull request.
4. Decisions and rationale go in section 20 of the spec; ambiguities found while implementing go in `docs/implementation-findings/`, numbered at the end of the matching file.

If you wrote an independent implementation, an interoperability report (issue template "Interoperability report") with the failing vector name is the most useful contribution of all.

## Pull requests

Keep them small and focused. The pull request template lists the checks. CI must pass: Rust (fmt, clippy, tests, vectors, regeneration), JavaScript, Python (3.8 and 3.12), site and docs, CDDL validation and workflow lint. Commit messages say what changed and why, in plain language.
